# BLUPRNT Lab コーディングルール

この文書は、BLUPRNT Lab 全体で守るコーディング規約、命名規則、フォルダ構成、テスト、レビュー、保守性のルールを定義します。

技術スタックが未決定の領域では、特定言語の慣例よりも、ドメイン境界、型安全、テスト可能性、監査可能性を優先します。言語固有ルールは採用技術のADR確定後に追加します。

---

## 1. 基本原則

1. **正しさを優先する** — 動作することだけでなく、医学・権限・版のルールを満たすこと
2. **単純さを優先する** — 必要性が確認されていない抽象化や分散構成を作らないこと
3. **境界を明確にする** — ドメイン、外部サービス、入出力、永続化を分離すること
4. **型と構造で制約する** — コメントやプロンプトだけに重要ルールを依存させないこと
5. **失敗を明示する** — 不明・不足・矛盾を成功として扱わないこと
6. **変更を追跡できるようにする** — コンテンツ、プロンプト、API、DB、成果物に版を持たせること
7. **テスト可能にする** — AIや外部APIなしで主要な業務ルールを検証できること
8. **秘密を持ち込まない** — ソース、ログ、サンプル、エラーへ秘密情報を残さないこと
9. **10年運用を前提にする** — 交換、移行、廃止、復元を設計に含めること
10. **共通利用を先に検討する** — 3システムで同じ意味を持つ処理は共通化を提案すること

## 2. アーキテクチャ規約

### 2.1 レイヤー

各システムは原則として次のレイヤーに分けます。

| レイヤー | 責務 | 禁止事項 |
|---|---|---|
| `domain` | 業務モデル、値オブジェクト、ポリシー、ドメインエラー | Web、DB、AI SDK、ファイルシステムへの直接依存 |
| `application` | ユースケース、処理順序、トランザクション境界 | HTTP形式やベンダー固有レスポンスの保持 |
| `infrastructure` | DB、AI、検索、ストレージ、PDF・動画エンジン | 業務判断の埋め込み |
| `api` / `interfaces` | 入力検証、認証、レスポンス変換 | ドメインルールの重複実装 |
| `validation` | 構造・出力・品質の機械検証 | 医学的最終承認の代替 |

依存関係は `interface → application → domain` を基本とし、`infrastructure` は定義済みのインターフェースを実装します。

### 2.2 ドメイン境界

- `Medical Knowledge Engine`、`NationalExam`、`TrainingVideo` は互いの内部モジュールをimportしない
- 他ドメインのDBテーブルを直接読み書きしない
- 再利用は `Packages` の公開契約、Platform API、版付きイベントを利用する
- 共有パッケージへ特定ドメインだけの都合を持ち込まない
- 新機能の設計時に、3システムで共通利用できないかを必ず確認する
- 2か所で使われたことだけを理由に自動共通化せず、意味と変更理由が共通か確認する
- 循環依存を禁止する

### 2.3 外部サービス

- AI、DB、検索、ストレージ、PDF、動画処理はアダプター越しに利用する
- ベンダー固有モデルをドメインモデルとして公開しない
- タイムアウト、再試行、キャンセル、エラー変換を接続境界で扱う
- 再試行は回数と対象エラーを限定し、非冪等操作を自動再試行しない
- 外部障害時に承認済みデータを破壊・上書きしない

### 2.4 10年運用と共通利用の判断

新しい機能の実装前に、設計レビューで次を回答します。

1. NationalExam、TrainingVideo、Medical Knowledge Engine のどこで使うか
2. 将来、他の2システムでも同じ意味で利用する可能性があるか
3. ドメイン固有機能、共通ライブラリ、共通サービスのどれに置くべきか
4. 外部サービスや技術を将来交換できるか
5. API・データ形式を変更するとき、既存データをどう移行するか
6. 旧版をいつまで読み取れるようにするか
7. 障害時に復元・再実行・ロールバックできるか
8. 10年後に担当者が変わっても、文書とテストから目的を理解できるか

配置判断は次を基準にします。

| 配置 | 選ぶ条件 | 例 |
|---|---|---|
| ドメイン内部 | 1システム固有の業務判断 | 問題の正答一意性、動画タイムライン、用語分類テンプレート |
| `Packages/` | 状態を持たず、複数システムで同じ意味を持つ処理 | ID、版、出典、JSON契約、エラー、入力検証 |
| `Platform/` | 共通データ、権限、履歴、処理状態を一元管理する機能 | 認証、原資料、レビュー、AIジョブ、監査、成果物管理 |

共通化の提案には、利用予定システム、公開インターフェース、所有者、版、テスト、変更・廃止方針を含めます。

長期運用を理由に、利用予定のないマイクロサービス、汎用フレームワーク、抽象化層を先に作りません。まずは境界が明確なモジュールとして実装し、独立運用が必要になった時点でサービス分割を検討します。

## 3. フォルダ構成

### 3.1 トップレベル

```text

├── README.md
├── Docs/
├── MedicalPDF/
├── NationalExam/
├── TrainingVideo/
├── Assets/
├── Templates/
├── Apps/               # 実装時に必要になった場合
├── Platform/           # 実装時に必要になった場合
├── Packages/           # 実装時に必要になった場合
└── Infrastructure/     # 実装時に必要になった場合
```

### 3.2 Pythonドメインの標準

```text
<Domain>/
├── README.md
├── docs/
├── src/
│   └── <package_name>/
│       ├── api/
│       ├── application/
│       ├── domain/
│       ├── infrastructure/
│       ├── validation/
│       └── config/
├── templates/
├── schemas/
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── contract/
│   ├── golden/
│   └── security/
├── samples/
└── pyproject.toml
```

### 3.3 配置ルール

- 本番コードは `src/` 配下へ置く
- テストは対象レイヤーと種類を判別できる場所へ置く
- テンプレート、プロンプト、JSON Schemaをソースコードへ長い文字列として埋め込まない
- 生成物、キャッシュ、一時ファイルをリポジトリへコミットしない
- 患者情報や機密情報を `samples/`、`fixtures/`、スナップショットへ置かない
- 空フォルダを将来予定だけで作らない
- `utils`、`helpers`、`common` を無制限な置き場にしない
- 1ファイルに複数レイヤーの責務を混在させない

## 4. 命名規則

### 4.1 共通

- 名前から業務上の意味と単位が分かるようにする
- 省略語は医学・技術分野で広く合意されたものだけを使う
- `data`、`info`、`manager`、`processor` のような曖昧な名前を単独で使わない
- 真偽値は `is_`、`has_`、`can_`、`should_` などで始める
- 時刻は `*_at`、日付は `*_date`、件数は `*_count` とする
- IDは `*_id` とし、ユーザー名や疾患名をIDへ埋め込まない
- 単位を持つ数値は `duration_seconds`、`size_bytes` のように単位を含める
- 版は `version`、スキーマ版は `schema_version` として区別する

### 4.2 Python

| 対象 | 規則 | 例 |
|---|---|---|
| パッケージ・モジュール | `snake_case` | `source_registry.py` |
| 関数・変数 | `snake_case` | `resolve_disease_name` |
| クラス・型 | `PascalCase` | `EvidenceReference` |
| 定数 | `UPPER_SNAKE_CASE` | `MAX_REFERENCE_COUNT` |
| 非公開要素 | 先頭 `_` | `_normalize_alias` |
| テスト | `test_<condition>_<expected>` | `test_ambiguous_name_returns_candidates` |

### 4.3 TypeScript／フロントエンド

採用時は次を基本とします。

| 対象 | 規則 | 例 |
|---|---|---|
| コンポーネント・型 | `PascalCase` | `ReviewStatusBadge` |
| 関数・変数 | `camelCase` | `loadContentVersion` |
| 定数 | `UPPER_SNAKE_CASE` | `MAX_UPLOAD_SIZE_BYTES` |
| ディレクトリ | `kebab-case` | `review-workflow/` |
| Hook | `use`で開始 | `useReviewQueue` |

### 4.4 DB・JSON・API

- DBテーブル・カラムは `snake_case`
- JSONフィールドは全システムで `snake_case` に統一する
- DBテーブルは複数形、ドメインクラスは単数形を基本とする
- APIパスは名詞の複数形と `kebab-case` を使う
- 動詞はHTTPメソッドで表し、必要な業務操作だけ明示的なactionとする
- エラーコードは安定した `UPPER_SNAKE_CASE`
- イベント種別は `domain.entity.event.v1` 形式を基本とする

## 5. 実装規約

### 5.1 関数とクラス

- 1つの関数は1つの目的を持つ
- 入力、出力、副作用を明確にする
- 長大な条件分岐は名前付きポリシーへ分離する
- 継承よりコンポジションを優先する
- 不変条件はコンストラクタまたはファクトリで検証する
- `None`、空文字、空配列の意味を曖昧にしない
- 例外を握りつぶさない
- 予期される業務エラーと予期しない障害を区別する
- コメントは「何をしているか」より「なぜこの制約が必要か」を記す

### 5.2 型

- 公開関数、ユースケース、外部境界には型を付ける
- 生の辞書をドメイン内部で受け回さず、型付きモデルへ変換する
- 文字列だけで状態を表さず、列挙型または値オブジェクトを使う
- 金額、日付、期間、文書ID、根拠位置を単なる文字列で混同しない
- 外部APIレスポンスは検証後に内部モデルへ変換する
- AI出力は必ずJSON Schemaまたは同等の型検証を通す

### 5.3 状態と副作用

- ドメイン状態の更新はユースケースを経由する
- 承認済み版を直接編集しない
- DB更新とファイル生成を1つの暗黙的処理にしない
- 長時間処理は状態付きジョブとして扱う
- 冪等性キーまたは同等の仕組みで重複実行を防ぐ
- 現在時刻、乱数、外部通信はテストで差し替え可能にする

### 5.4 設定と秘密情報

- 設定は環境変数または設定サービスから読み込む
- `.env` の実値をコミットしない
- APIキー、パスワード、署名鍵をコード、テスト、ログへ書かない
- デフォルト設定は安全側にする
- 開発・検証・本番のデータ領域と資格情報を分離する
- 秘密情報をエラー本文やデバッグ表示へ含めない

## 6. エラー設計

### 6.1 エラー分類

| 分類 | 例 | 扱い |
|---|---|---|
| Validation | 疾患名不正、必須値不足 | 利用者が修正可能な内容を返す |
| Ambiguous | 疾患名候補が複数 | 候補を返し推測しない |
| Insufficient Evidence | 根拠不足 | 生成を止め、資料追加またはレビューを要求 |
| Conflict | 情報源の矛盾、版競合 | 自動統合せず人へ通知 |
| Forbidden | 権限不足、権利条件違反 | 操作を拒否し監査記録を残す |
| External Failure | AI、検索、PDF、動画サービス障害 | 限定的な再試行または安全な失敗 |
| Internal Failure | 想定外の障害 | 相関IDを返し、詳細は安全なログへ保存 |

### 6.2 エラーレスポンス

- 安定したエラーコード
- 人が理解できるメッセージ
- 機械処理可能な詳細
- 相関ID
- 再試行可能かどうか
- 利用者が次に取れる行動

スタックトレース、内部パス、SQL、秘密情報、プロンプト全文を利用者へ返しません。

---

## 7. ログと監査

- ログはデバッグ・運用目的、監査ログは責任追跡目的として分離する
- すべてのリクエストとジョブに相関IDを持たせる
- AIジョブにはプロンプト版、モデル識別子、根拠ID、評価結果を記録する
- コンテンツ変更には操作者、変更前後の版、理由を記録する
- 個人情報、患者情報、原資料全文、AI秘密情報を通常ログへ出さない
- ログ項目は構造化し、自由文へ重要識別子を埋め込まない
- ログ保存期間とアクセス権を環境ごとに定義する

## 8. テスト規約

### 8.1 必須テスト層

| 種類 | 目的 |
|---|---|
| Unit | ドメインルール、値、分岐を高速に確認 |
| Integration | DB、検索、ストレージ、レンダラーとの連携 |
| Contract | API、イベント、JSON Schemaの互換性 |
| Golden | 医学内容、AI出力、PDF・動画結果の回帰評価 |
| Security | 権限、入力攻撃、プロンプト攻撃、情報漏えい |
| End-to-End | 主要利用フローの受入確認 |

### 8.2 テストルール

- 不具合修正には再現テストを追加する
- 外部AIの実呼出しを通常の単体テストに含めない
- AIは偽実装・記録済み応答・評価ジョブを使い分ける
- テストが実行順序や共有状態に依存しないようにする
- 日付・時刻・乱数を固定可能にする
- 正常系だけでなく不足、曖昧、矛盾、権限不足、外部障害を検証する
- PDF・動画はファイル生成成功だけでなく内容と物理品質を検証する
- カバレッジ率だけを品質目標にせず、重要ルールの網羅を確認する

## 9. Git・レビュー規約

### 9.1 変更単位

- 1つの変更は1つの目的にまとめる
- リファクタリングと仕様変更を可能な限り分ける
- 生成物、キャッシュ、秘密情報をコミットしない
- 大容量素材はGitへ直接保存せず、採用した大容量管理方式を使う

### 9.2 コミットメッセージ

Conventional Commitsを基本とします。

- `feat:` 機能追加
- `fix:` 不具合修正
- `docs:` 文書変更
- `refactor:` 外部動作を変えない構造改善
- `test:` テスト追加・修正
- `chore:` ビルド・依存関係・保守作業
- `security:` セキュリティ修正

メッセージには変更内容だけでなく、必要に応じて理由と影響範囲を記載します。

### 9.3 レビュー

- CIが成功してからマージする
- 医学仕様の変更は医療監修者または医学ルール所有者が確認する
- API、DB、イベントの破壊的変更には移行計画を付ける
- セキュリティ、権限、個人情報の変更は専用チェックを行う
- 自己レビューで不要なデバッグ、秘密、生成物、無関係な変更を除く
- レビュー指摘をコードコメントだけで終わらせず、必要ならルール文書へ反映する

## 10. API・スキーマ互換性

- すべての外部入出力を検証する
- APIとイベントに明示的なバージョン方針を持つ
- 任意フィールドの追加でも利用側への影響を契約テストで確認する
- 列挙値追加を常に後方互換と仮定しない
- フィールド削除・意味変更・型変更を同じ版で行わない
- 日時はタイムゾーン付きISO 8601文字列を使用する
- 浮動小数点で金額や厳密値を表さない
- `null`、省略、空文字、空配列の意味をスキーマで定義する

JSONの詳細は `Docs/prompt_rules.md` を参照します。

---

## 11. 依存関係管理

- 新しい依存ライブラリには利用目的を1つ以上明示する
- 標準ライブラリや既存依存で十分な場合は追加しない
- 公式配布元、保守状況、ライセンス、脆弱性、更新頻度を確認する
- 依存バージョンをロックし、更新は専用変更として行う
- メジャー更新では移行ガイドと回帰テストを確認する
- 未使用依存を残さない
- 実行時依存と開発時依存を分離する
- AIやPDF・動画の重い依存は専用ワーカーへ隔離できるようにする

---

## 12. 保守性を高めるルール

- 重複より先に不適切な抽象化を警戒する
- 複雑な処理には入口、出口、不変条件、失敗条件を文書化する
- 暗黙のデフォルトを減らし、安全に影響する値は明示する
- Feature Flagには所有者と削除期限を設定する
- TODOには理由、追跡先、期限または削除条件を付ける
- 非推奨APIには移行先と削除予定を記載する
- DB、API、プロンプト、成果物の版を独立して管理する
- 運用で手作業が必要な機能にはRunbookを用意する
- 同じ障害が繰り返される場合は、注意書きではなく仕組みで防ぐ
- 設計と実装がずれた場合は、どちらを正とするか判断して同時に修正する

---

## 13. Definition of Done

コード変更は、該当する次の条件を満たしたときに完了です。

- 要件と受入条件を満たす
- ドメイン境界と依存方向を守る
- 入力・出力・失敗を型で表現する
- 必要な単体・結合・契約・セキュリティテストがある
- Lint、Format、型検査、テストが成功する
- ログへ秘密・患者情報・原文全文を出さない
- API、DB、プロンプトの変更に移行・互換性検討がある
- 医学仕様の変更に必要なレビューがある
- README、設計文書、ADRが実装と一致する
- 不要な依存、デバッグコード、生成物を含まない

速度やファイル数を理由に、この完了条件を省略しません。
