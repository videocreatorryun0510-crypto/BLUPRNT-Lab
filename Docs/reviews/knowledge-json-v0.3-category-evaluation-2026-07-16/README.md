# Knowledge JSON Version 0.3 カテゴリ横断評価

評価日：2026-07-16

## 1. 評価目的

Knowledge JSON Version 0.3を6カテゴリの代表用語で実際に生成し、Schemaに適合するかだけでなく、各カテゴリの国家試験学習に必要な医学的事実を十分に保持できる構造かを確認した。

今回の評価は構造評価であり、生成された医学的内容の承認ではない。すべてOpenAIによる未確認の下書きであり、正本として利用する前に出典確認と医学レビューが必要である。

## 3. 全体評価

### 機能している点

- 用語、カテゴリ、国家試験科目を全カテゴリ共通の形式で保持できる
- すべての医学的事実にclaim IDを付けられる
- 国家試験メタデータ、出典、Publisher優先指定の共通保存先を持つ
- 検査項目は、目的、検体、測定方法、測定原理、高値・低値、組み合わせ、注意点を区別できる
- 検査項目では、病態と代表疾患を別々に保持できる

### 構造上の主な不足

疾患、染色法、微生物、寄生虫にはカテゴリ専用構造がない。生成された内容はすべて`definitions`、`mechanisms`、`characteristics`へ入るため、Schemaには適合しても、各Publisherが必要な情報を安定して取り出せない。

例えば黄色ブドウ球菌では、カタラーゼ、コアグラーゼ、耐性機構、毒素が`mechanisms`へ混在した。医学的事実が存在しても、事実の役割を機械的に区別できないことが問題である。

### 空欄の評価

`exam_metadata`、`evidence`、`publish_targets`が空であることは、今回のPhaseでは意図どおりである。AIに出典や国家試験頻度を推測させない安全な状態になっている。

ASTとHbA1cの`reference_ranges`も空だった。出典なしで数値を生成しない点は安全だが、実用化までには承認済み資料から基準範囲や臨床判断値を登録する工程が必要である。

## 4. カテゴリ別レビュー

### 4.1 AST（検査項目）

#### 十分に機能した項目

- 検査目的
- 血清・血漿という検体
- JSCC標準化対応法とIFCC法の分離
- 測定方法と測定原理のclaim IDによる関連付け
- 肝細胞障害などの病態と、急性肝炎などの代表疾患の分離
- ALT、CK、LDとの組み合わせ
- 溶血、測定法差、ビタミンB6欠乏に関する注意

#### 不足している項目

- 出典付きの基準範囲
- 単位と報告形式
- 検体保存条件
- 分析前・分析中干渉の構造化
- 測定法間差や標準化の詳細
- 低値を示す病態・疾患の扱い方
- 必要に応じたアイソザイムや経時変化

#### 不要または整理すべき項目

明確に削除すべき共通項目はない。ただし、`core_facts`と検査項目専用領域に同じ事実を重複させない運用規則が必要である。

#### 今後追加すべき項目

- `reporting`：単位、報告方式
- `standardization`：標準化体系、トレーサビリティ
- `analytical_interferences`：溶血、乳び、黄疸など
- `clinical_decision_limits`：基準範囲とは異なる判断値
- 任意の`time_course`、`isoenzymes`

### 4.2 HbA1c（検査項目）

#### 十分に機能した項目

- 慢性高血糖の評価という目的
- 全血、抗凝固剤という検体情報
- HPLC法、免疫測定法、酵素法の分離
- 各測定法と原理の対応
- 赤血球寿命短縮と溶血性貧血の分離
- 血糖、グリコアルブミンとの組み合わせ
- 輸血、溶血、異常ヘモグロビン、鉄欠乏の注意

#### 不足している項目

- NGSP値とIFCC値の報告単位
- 標準化体系と換算関係
- 診断に用いる臨床判断値
- 出典付きの基準範囲
- 測定法ごとの異常ヘモグロビン干渉
- 検体保存条件
- 血糖を反映する期間

#### 不要または整理すべき項目

現在の`standardizing_body`を各日常測定法へ直接付ける構造は単純すぎる。HPLC法などの方法名そのものと、IFCCへのトレーサビリティは別の概念として保持する方が正確である。

#### 今後追加すべき項目

- 測定方法から独立した`standardization_and_traceability`
- `reporting_systems`と単位
- `conversion_relations`
- `clinical_decision_limits`
- 方法別の`analytical_interferences`

### 4.3 巨赤芽球性貧血（疾患）

#### 十分に機能した項目

定義、DNA合成障害、核・細胞質成熟乖離、無効造血、末梢血像、骨髄像、ビタミンB12欠乏と葉酸欠乏の違いは事実として保存できた。

#### 不足している項目

- 病因・原因
- 病態生理
- 症状・身体所見
- CBC、網赤血球、生化学などの主要検査所見
- 末梢血形態と骨髄形態
- 診断に用いる検査
- 鑑別疾患
- 原因疾患との関連
- 合併症

これらの一部は文章として生成されているが、専用の保存欄がないため、機械的に区別できない。

#### 不要または整理すべき項目

詳細な治療法を全疾患の必須項目にする必要はない。臨床検査技師国家試験との関連がある場合だけ、任意の医学的事実として扱う。

専用テンプレート導入後は、疾患固有の事実を`mechanisms`と`characteristics`へ重複保存しない。

#### 今後追加すべき項目

- `etiologies`
- `pathophysiology`
- `clinical_findings`
- `laboratory_findings`
- `morphologic_findings`
- `diagnostic_tests`
- `differential_diagnoses`
- `complications`

### 4.4 Gram染色（染色法）

#### 十分に機能した項目

目的、細胞壁との関係、基本工程、陽性・陰性の色、抗酸菌とマイコプラズマの注意は事実として保存できた。

#### 不足している項目

- 対象検体と標本
- 固定法
- 使用試薬
- 操作順序
- 反応時間
- 脱色条件
- 判定結果
- 精度管理
- 過脱色・脱色不足などの失敗原因
- 適用できない微生物や限界

#### 不要または整理すべき項目

専用テンプレート導入後、染色工程を`mechanisms`へ文章で重複保存する必要はない。工程、原理、結果を分離する。

#### 今後追加すべき項目

- `purposes`
- `applicable_specimens`
- `reagents`
- `procedure_steps`
- `staining_principles`
- `result_interpretations`
- `quality_controls`
- `error_causes`
- `limitations`

### 4.5 黄色ブドウ球菌（微生物）

#### 十分に機能した項目

グラム陽性球菌、ブドウ房状配列、通性嫌気性、カタラーゼ、コアグラーゼ、マンニット分解、選択培地、毒素、MRSAに関する事実は保存できた。

#### 不足している項目

- 分類
- 形態・染色性
- 発育条件
- 培地と集落性状
- 生化学的同定
- 抗原、毒素、病原因子
- 代表疾患
- 検査材料
- 検出・同定方法
- 薬剤感受性・耐性機構
- 感染対策

#### 不要または整理すべき項目

カタラーゼやコアグラーゼは不要な事実ではないが、`mechanisms`ではなく`identification_tests`へ置くべきである。毒素、耐性機構、同定性状を同じ配列へ混在させない。

#### 今後追加すべき項目

- `taxonomy`
- `morphology_and_staining`
- `growth_conditions`
- `culture_characteristics`
- `identification_tests`
- `virulence_factors_and_toxins`
- `associated_diseases`
- `diagnostic_specimens_and_methods`
- `antimicrobial_resistance`
- `infection_control`

### 4.6 蟯虫（寄生虫）

#### 十分に機能した項目

分類、寄生部位、夜間産卵、経口感染、自家感染、肛門周囲掻痒、セロハンテープ法、虫卵形態は事実として保存できた。

#### 不足している項目

- 分類群
- 終宿主・中間宿主
- 寄生部位
- 感染型
- 診断型
- 生活環
- 感染経路
- 検査材料と採取条件
- 成虫・虫卵・幼虫の形態
- 検査方法
- 症状
- 予防

#### 不要または整理すべき項目

詳細な治療法を全寄生虫の必須項目にする必要はない。国家試験上必要な場合にだけ任意項目として扱う。

生活環、感染経路、診断法を`mechanisms`と`characteristics`へ混在させない。

#### 今後追加すべき項目

- `taxonomy`
- `hosts`
- `habitat`
- `infective_stage`
- `diagnostic_stage`
- `life_cycle_steps`
- `transmission_routes`
- `morphologic_stages`
- `specimens_and_collection`
- `diagnostic_methods`
- `clinical_findings`
- `prevention`

## 5. Version 1.0へ向けた改善優先順位

### 最優先

1. 疾患、染色法、微生物、寄生虫のカテゴリ専用テンプレートを設計する
2. カテゴリごとの必須項目と、空欄を許可する条件を決める
3. Schema適合とは別に「カテゴリとして十分か」を確認する完全性検証を追加する
4. claim IDをAIの文章表現から独立して維持できるID台帳と更新手順を決める
5. 基準範囲、臨床判断値、単位、測定法、出典を正しく関連付ける

### 次に必要

6. 検査項目の標準化、トレーサビリティ、報告単位、干渉物質を構造化する
7. 医学的な関連を表す共通のKnowledge ID関係を設計する
8. 用語、単位、検体、微生物、寄生虫などの表記揺れを抑える管理語彙を作る
9. 同じ用語を複数回生成し、カテゴリ判定と項目充足率が安定するか回帰テストする
10. Version 0.3サンプルから1.0へ移行する規則と互換性テストを用意する

### Knowledge JSONの外側で必要

- 出典確認、医学レビュー、承認、差戻しを管理する台帳
- AI生成履歴と使用モデルを管理する監査記録
- 国家試験CSVから`exam_metadata`を作る処理

これらは医学的事実の正本へ混ぜず、既存方針どおり別の管理層に置く。

## 6. CTO自己レビュー

Version 0.3は、共通知識基盤の骨格と検査項目テンプレートの試作品としては合格である。一方、全カテゴリ共通の完成形としては未完成である。

最大の問題は、`generic_facts_v0.3`が柔軟すぎることである。柔軟な配列はどの事実でも保存できるが、Publisherが「生活環だけ」「培地だけ」「主要検査所見だけ」を安全に取り出せない。Version 1.0ではカテゴリ固有の事実を明確な欄へ分け、共通部分は現在のまま再利用する設計が妥当である。

Version 1.0の完成条件は、単に6件がSchemaに通ることではない。各カテゴリの必須情報が所定の欄に入り、出典とclaimが結び付き、同じ用語を再生成してもIDと関連が壊れないことまで確認する必要がある。

今回は評価のみを行い、Knowledge JSON Schema、プロンプト、Workbench、Publisherには変更を加えていない。
