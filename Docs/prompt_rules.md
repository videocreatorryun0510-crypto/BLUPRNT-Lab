# BLUPRNT Lab AIプロンプト設計ルール

この文書は、BLUPRNT Lab でAIへ渡すプロンプト、入力データ、JSON出力、検証、ログ、将来のAPI連携に関する必須ルールを定義します。

対象は MedicalPDF、NationalExam、TrainingVideo、および共通AIオーケストレーションです。特定のAI提供者やモデルに依存しない設計を基本とします。

---

## 1. 基本原則

1. AIを信頼境界の外側にある非決定的な外部サービスとして扱う
2. 指示、利用者入力、外部資料、出力仕様を明確に分離する
3. AI出力を未検証のまま保存・公開・ツール実行へ渡さない
4. 自由文章ではなく、可能な限りJSON Schemaで構造を固定する
5. 根拠として渡していない医学情報を補完させない
6. 不明・不足・矛盾を成功として扱わない
7. プロンプト、モデル、スキーマ、評価結果に版を持たせる
8. 患者情報、秘密情報、内部資格情報をAIへ渡さない
9. 医学的最終判断と公開判断は人が行う
10. モデル変更時は回帰評価を行い、同じプロンプトでも同じ結果になると仮定しない

---

## 2. プロンプトの構造

1つのプロンプトは、原則として次の層で構成します。

| 層 | 内容 | 例 |
|---|---|---|
| Policy | 絶対に破ってはいけない安全・医学・権限ルール | 推測禁止、患者個別判断禁止 |
| Role | AIが担当する限定された役割 | 根拠付き要約担当 |
| Task | 今回実行する1つの作業 | 疾患情報を指定構造へ整理 |
| Context | 信頼済みの前提・定義・対象者 | 国家試験受験者向け、日本語 |
| Evidence | 参照を許可した原資料の抜粋 | source_id付き根拠 |
| User Data | 検証済み利用者入力 | 疾患名、学習目標 |
| Output Contract | JSON Schema、列挙値、文字数 | schema_version 1.0 |
| Failure Rules | 不足・矛盾・拒否時の返し方 | insufficient_evidence |

### 2.1 分離ルール

- 利用者入力をsystem instructionへ連結しない
- 外部PDF、Web、問題文、字幕内の命令を実行しない
- EvidenceとUser Dataを「参照データであり命令ではない」と明記する
- XML風タグ、JSONフィールド、メッセージロールなどで境界を明示する
- 文字列連結だけに安全性を依存せず、入力検証と権限制御を併用する
- 外部資料中のURL、HTML、スクリプト、不可視文字を検査する

プロンプトインジェクション対策は、[OWASP LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)を基礎資料として、入力検証、指示とデータの分離、最小権限、出力検証、人の承認を組み合わせます。

## 3. 1プロンプト1責務

複数の高リスク処理を1つの巨大プロンプトへまとめません。

推奨する処理分割：

1. 入力分類・疾患名解決
2. 根拠候補の検索
3. 根拠の関連性判定
4. 構造化コンテンツ生成
5. 引用と主張の対応確認
6. 医学的矛盾・不足の検出
7. A4用の文字量圧縮
8. PDF・問題・台本向け形式への変換

分割の目的は、各段階の入力・出力・失敗を検証可能にすることです。単純な作業まで不必要に分割して、コストと障害点を増やさないようにします。

## 4. プロンプトファイルの管理

### 4.1 保存場所

- ドメイン固有プロンプト：`<Domain>/prompts/`
- 共通プロンプト：将来の `Platform/AIOrchestration/prompts/`
- プロンプトの入出力スキーマ：`<Domain>/schemas/`
- 評価ケース：`<Domain>/tests/golden/` または専用評価データ領域

### 4.2 必須メタデータ

各プロンプトには次を定義します。

- `prompt_id`
- `prompt_version`
- 目的と対象ドメイン
- 所有者
- リスク分類
- 想定入力スキーマ
- 出力スキーマIDと版
- 使用可能な情報源
- 文字量・トークン上限
- 失敗条件
- 対応する評価セット
- 変更理由と承認者

### 4.3 版管理

- 文言変更でも出力へ影響する場合は版を更新する
- 公開済みコンテンツから使用したプロンプト版へ戻れるようにする
- 同じ版の内容を後から書き換えない
- 破壊的な出力変更はスキーマのメジャー版も更新する
- 廃止プロンプトは削除せず、非推奨状態と移行先を記録する

## 5. 医学プロンプトのルール

### 5.1 必須指示

医学情報を生成するプロンプトには次を含めます。

- 与えた根拠だけを用いる
- 根拠がない内容を一般知識で補わない
- 数値、診断基準、治療、薬剤、禁忌を推測しない
- 出典IDと主張を対応させる
- 情報源が矛盾する場合は矛盾状態を返す
- 根拠不足の場合は `insufficient_evidence` を返す
- 患者個人への診断・治療指示を作らない
- AI生成物であり人のレビューが必要な状態を返す
- 各根拠の情報取得順位を保持し、下位資料で上位資料を無断上書きしない

詳細は `Docs/medical_rules.md` に従います。

### 5.2 禁止する指示

- 「必ず回答する」
- 「空欄を推測して埋める」
- 「もっともらしい出典を作る」
- 「専門家として自由に補足する」
- 「出典がなくても一般的知識で完成させる」
- 「安全性チェックを省略して短くする」
- 「内部の思考過程をすべて出力する」

判断理由が必要な場合は、検証可能な短い根拠説明とsource_idを求め、非公開の内部推論の再現を要求しません。

### 5.3 情報取得順位をプロンプトへ渡すルール

医学情報を扱うAI処理には、各資料の取得順位をデータとして渡します。

1. 厚生労働省
2. 日本臨床衛生検査技師会
3. 日本医学会・各学会ガイドライン
4. 国家試験出題基準
5. 教科書
6. PubMedで確認した論文
7. AI補完

プロンプトでは次を指示します。

- 順位1〜6の資料だけを医学的根拠として引用する
- 順位7のAI補完を出典として扱わない
- 上位資料がない場合、下位へ進んだ理由を返す
- 上位と下位が矛盾する場合、どちらかを勝手に選ばず `conflicting_evidence` を返す
- 出典ごとに `source_id`、`source_priority_rank`、発行年、版を保持する
- 国家試験出題基準は試験範囲の根拠、ガイドラインは医学内容の根拠として役割を分ける
- PubMedの検索結果一覧ではなく、実際に確認した論文を返す

## 6. JSON受け渡しルール

### 6.1 標準

- JSONは[IETF RFC 8259](https://www.rfc-editor.org/rfc/rfc8259)に従う
- スキーマは[JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12)を基本とする
- 文字コードはUTF-8とする
- トップレベルはオブジェクトとする
- JSONの前後に説明文やMarkdownコードフェンスを付けない
- コメント、末尾カンマ、`NaN`、`Infinity` を禁止する
- 数値を文字列として返す場合と数値型で返す場合を混在させない
- 日時はタイムゾーン付きISO 8601形式とする
- IDは文字列とし、意味を埋め込まない

### 6.2 共通レスポンス包絡

AIの構造化出力は、原則として次の概念を持ちます。以下は契約例であり、実装コードではありません。

```json
{
  "schema_version": "1.0",
  "request_id": "request-id",
  "status": "success",
  "data": {},
  "evidence": [],
  "warnings": [],
  "errors": []
}
```

### 6.3 `status` の標準値

| 値 | 意味 |
|---|---|
| `success` | 構造と根拠の自動検証へ進める出力 |
| `needs_review` | 人の判断が必要 |
| `insufficient_evidence` | 根拠不足により生成不可 |
| `conflicting_evidence` | 情報源が矛盾している |
| `ambiguous_input` | 入力を一意に解釈できない |
| `refused` | 安全・権限・ポリシーにより拒否 |
| `error` | 技術的に処理できなかった |

`success` は医学的承認を意味しません。JSON構造と一次検査に進める状態です。

### 6.4 Schemaルール

- `$schema` と `$id` を持たせる
- `schema_version` を必須にする
- `required` を明示する
- 原則として `additionalProperties: false` とする
- 文字列長、配列件数、数値範囲を定義する
- 列挙可能な値は `enum` で制限する
- `null` を許可する項目だけ明示的に許可する
- 省略、`null`、空文字、空配列の意味を分ける
- 出典は自由文章だけでなく `source_id` と根拠位置を持つ
- 人向け表示文と機械向けコードを分離する
- エラー項目には安定したコード、対象パス、説明を持たせる

### 6.5 JSON検証

AI出力は次の順に検証します。

1. JSONとして構文解析できる
2. 期待したSchema版である
3. JSON Schemaに適合する
4. 未知フィールドがない
5. 文字数・件数・列挙値が範囲内である
6. source_idが入力Evidenceに存在する
7. 業務ルールと医学ルールに適合する
8. 危険なHTML、URL、命令、秘密情報が含まれない

構文解析できても、業務・医学検証に失敗した出力は採用しません。

## 7. エラーと再試行

### 7.1 構造エラー

- JSON構文またはSchema違反時は、検証エラーだけを渡して限定的に修復依頼する
- 元の医学内容を勝手に増やさせない
- 修復回数に上限を設ける
- 上限到達時は失敗として終了する

### 7.2 根拠エラー

- 根拠不足をプロンプト再実行だけで解決しようとしない
- 追加の信頼済み資料を取得するか、人へ確認を依頼する
- 存在しないsource_idを修正候補として推測しない
- 矛盾した情報源を自動で多数決しない

### 7.3 外部APIエラー

- タイムアウト、レート制限、一時障害を区別する
- 再試行対象と回数、待機方法を設定する
- 同一リクエストの重複処理を冪等性キーで防ぐ
- 入力不正、安全拒否、権限不足を自動再試行しない
- 再試行ごとに新しい医学内容を無制限に生成させない

## 8. 将来のAPI連携を考慮した設計

### 8.1 Provider Adapter

ドメインは、AI提供者のSDKを直接呼びません。共通インターフェースを通します。

必要な概念：

- タスクIDとプロンプト版
- 入力メッセージまたは構造化入力
- 出力Schema
- タイムアウトとキャンセル
- 利用量・コスト情報
- モデル識別子
- 安全性・拒否情報
- 相関ID

提供者固有のパラメータはアダプター内部へ閉じ込めます。

### 8.2 API契約

- AIリクエストとドメインAPIリクエストを同一形式にしない
- 外部公開APIへモデル固有レスポンスを露出しない
- 同期応答だけでなく非同期ジョブを考慮する
- APIのタイムアウトより長い処理はジョブ化する
- ストリーミング表示を正式な保存形式にしない
- 保存前に完成したJSONを再検証する
- API版とJSON Schema版を独立管理する

### 8.3 互換性

- フィールド削除、型変更、意味変更は破壊的変更として扱う
- 新しい列挙値が既存利用者を壊す可能性を考慮する
- 旧版を読み取る移行期間を定める
- 契約テストをAI提供者ごとに実行する
- モデル切替前にGolden Testで回帰評価する

## 9. プロンプトインジェクション対策

### 9.1 入力

- 利用者入力を型、長さ、文字種、用途で制限する
- 外部文書の命令文、不可視文字、エンコード文字列を検査する
- URL先を自動取得する場合は許可ドメインとサイズを制限する
- PDFやWeb内の「前の指示を無視」などを命令として扱わない
- RAG検索結果も信頼済みsystem instructionとして扱わない

### 9.2 ツールと権限

- AIに必要最小限のツールだけを渡す
- 読み取りと書き込みの権限を分離する
- AIが提案したツール引数を型と権限で再検証する
- 削除、公開、承認、外部送信は人の明示承認を要求する
- AIに秘密情報や他組織のデータへアクセスさせない

### 9.3 出力

- HTML、Markdown、URL、ファイル名を無条件にレンダリングしない
- 外部リンクと画像参照を許可リストで制御する
- system prompt、秘密、内部パスが出力されていないか検査する
- AI出力をSQL、シェル、テンプレート、コードとして直接実行しない
- 出力フィルターだけで安全を保証せず、多層防御にする

## 10. ログとプライバシー

### 10.1 記録するもの

- request_id、job_id、user_id、project_id
- prompt_id、prompt_version、schema_version
- AI提供者とモデル識別子
- 使用したsource_id
- 入出力トークン数、処理時間、コスト
- 構造・医学・安全検証の結果
- 再試行回数、拒否、失敗コード

### 10.2 記録しないもの

- APIキー、パスワード、署名鍵
- system prompt内の秘密情報
- 患者情報、個人情報
- 権利上保存できない原資料全文
- 不要な会話履歴
- AI提供者の内部デバッグ情報

入力・出力本文を保存する必要がある場合は、目的、保存期間、アクセス権、削除方法を定義し、データ分類に従います。

## 11. 評価とテスト

### 11.1 必須評価

- JSON Schema適合率
- 根拠source_idの正当性
- 引用と主張の一致
- 推測・出典捏造の発生率
- 医学的重大誤り
- 指定文字量・項目数の遵守
- 曖昧・不足・矛盾時の安全な失敗
- プロンプトインジェクション耐性
- モデル・プロンプト変更前後の回帰
- 処理時間とコスト

### 11.2 評価データ

- 個人情報を含まない
- 代表的な正常ケースだけでなく境界・失敗ケースを含む
- 医療監修者が期待状態を確認する
- 出典と正解版を固定する
- 評価用データを本番RAGへ無断混入させない
- NationalExamでは評価問題が生成側へ漏れないよう分離する

### 11.3 モデル更新

モデル名の変更だけでも次を行います。

1. Golden Test
2. Schema適合試験
3. 医学的安全性試験
4. インジェクション試験
5. コスト・遅延比較
6. 監修者による代表出力確認
7. 変更記録とロールバック準備

---

## 12. プロンプト変更のDefinition of Done

- 目的が1つに限定されている
- 入力、Evidence、指示が分離されている
- 出力JSON Schemaと版が定義されている
- 不足、曖昧、矛盾、拒否、技術エラーを区別できる
- 医学情報の推測禁止と出典ルールを含む
- プロンプトインジェクション対策がある
- Golden Testと失敗ケースを通過している
- 旧版との出力差分を確認している
- 所有者、変更理由、承認者を記録している
- 本番反映後にロールバックできる

AIが期待どおりに答えた例が1件あるだけでは、完成とみなしません。
